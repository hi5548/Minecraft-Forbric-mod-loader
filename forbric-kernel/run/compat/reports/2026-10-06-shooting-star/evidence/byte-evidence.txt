Commands run on this box (JDK 21 `javap`), outputs verbatim. `NEO=/Applications/.minecraft/.forbric-build/out/neoforge-runtime.jar`
(the same jar the harness stages as `neoforge-runtime/neoforge-runtime.jar`), `MERGED=/Applications/.minecraft/.forbric-build/out/patched-mc-merged-1.21.1.jar`.

## 4. It is the MERGED base + companion runtime jar that carry this, not a Forge-only remnant

```
MERGED       patched-mc-merged-1.21.1.jar         entries= 23535  net/neoforged=    0  net/minecraftforge=    3
NEO-RUNTIME  neoforge-runtime.jar                 entries=  5030  net/neoforged= 1884  net/minecraftforge=   41
```

The merged jar itself carries **no** `net/neoforged` class — they all come from the companion runtime jar, which the
harness stages as `--runtimeJar neoforge-runtime/neoforge-runtime.jar`. So "does the merged base carry NeoForge's
biome_modifier registry/serializers?" is answered by the two jars **together**, and the answer is yes: the
`BiomeModifier` family, `NeoForgeRegistries$Keys`, `NeoForgeRegistries`, `NeoForgeRegistriesSetup`, `NeoForgeMod`,
`DataPackRegistryEvent`, `DataPackRegistriesHooks`, and the `ServerLifecycleHooks` reader are all present. Independently
re-checked by a sibling read-only census (class-set diff: merged ⊇ reference ∪ forge, i.e. no class the references have
is missing).

## 5. The client-side seam the fix touches

`KernelLifecycle.registerDataPackRegistries` (boot half) is where NeoForge's own listener is reached: it builds one
`DataPackRegistryEvent$NewRegistry`, posts it on the baseline bus, then on every published Neo mod bus, then calls the
package-private `process()` which flushes into `DataPackRegistriesHooks`. If the baseline bus does not exist yet — the
state a client's Fabric entrypoints leave it in — the post reaches nobody and the two keys are never declared. That is
the entire defect; the two edits in `diff.patch` change **when** that post happens and stop the one-shot from being spent
on a post to nobody. No new declaration code exists in this lane.
