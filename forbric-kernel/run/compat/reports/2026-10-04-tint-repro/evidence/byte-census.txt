## 2. 为什么它断**在合并基底上**(合并基底 vs NeoForge 的 `SpriteContents`)

合并基底 `net.minecraft.client.renderer.texture.SpriteContents` 有**两个**构造器:

```
public SpriteContents(ResourceLocation, FrameSize, NativeImage, ResourceMetadata);                       // 4 参
public SpriteContents(ResourceLocation, FrameSize, NativeImage, ResourceMetadata, ForgeTextureMetadata); // 5 参(Forge)
```
两个实体的逐字节:

```
 4 参:
   0: aload_0
   1: aload_1 ... aload 4
   6: aconst_null
   7: invokespecial #62  // Method "<init>":(Lnet/minecraft/resources/ResourceLocation;
                          //   Lnet/minecraft/client/resources/metadata/animation/FrameSize;
                          //   Lcom/mojang/blaze3d/platform/NativeImage;
                          //   Lnet/minecraft/server/packs/resources/ResourceMetadata;
                          //   Lnet/minecraftforge/client/textures/ForgeTextureMetadata;)V
  10: return                                    <-- 纯委托 stub,方法体里 0 个 PUTFIELD

 5 参:
   ...
  52: aload_0 ... createAnimatedTexture(...) -> putfield animatedTexture
  71: aload_0
  72: aload_3
  73: putfield #73  // Field originalImage:Lcom/mojang/blaze3d/platform/NativeImage;   <-- 唯一的 PUTFIELD 在这里
  76: aload_0 ... putfield byMipLevel
  91: aload_0
  92: aload 5
  94: putfield #491 // Field forgeMeta:Lnet/minecraftforge/client/textures/ForgeTextureMetadata;
  97: return
```

`SpriteContents` 上 `originalImage` 只有这一处 `PUTFIELD`(全类常量池核对)。NeoForge/Forge 两个 patched jar 里都一样存在 4 参/5 参这对,
差别只在**哪个实体装着方法体**:合并基底把 body 放在 **5 参**(Forge 的),把 4 参(vanilla 的签名)留成一行 `aconst_null` + 委托。

Mixin 对**不带描述符**的选择器(`method=["<init>"]`)绑定**第一个声明**的同名方法 —— 也就是那个 4 参 stub。
于是 `@At(FIELD … originalImage … opcode=181)` 在 4 参里**搜不到**,`@WrapOperation` 整条不附着。

内核自己的读数逐字(控制臂 `load-report.txt`,见 `load-report-sodium.txt`):

## 3. 为什么**不影响物品栏图标**(两个症状是两条路径)

物品/手持走 vanilla `ItemRenderer.renderQuadList`(合并基底,与 NeoForge 逐字节相同):
它按 quad 的 `tintIndex` 直接取 `ItemColors.getColor(stack, tintIndex)`,渲染类型取 `Sheets.cutoutBlockSheet()`
——**不经过 Sodium 的 chunk pass,也不经过 `getDowngradedPass`**。所以:

- 图标之所以"发灰",是 `ItemColors.getColor`/`BlockColors.getColor` 的 **Forge 委托键 vs NeoForge 原始键**失配(miss → `-1` → 白 → 灰),
  即 `ad9d5615` 修的那条;
- 世界之所以"泥土发黑",是 **Sodium cutout 降级**那条,`ad9d5615` 修不到。

两条在同一帧里就能分开:见 `frame-control__icon-grey.png` / `frame-fix__icon-green.png`
(同一确定性场景,图标灰→绿,而世界像素逐字节不变)。

## 4. 修复的形状(按内核既有约定,写在运行前)

内核已有**正好这一条**通用规则,只是没有命中 Sodium:

```
MixinStubRebind —— "Moves a mod's injector off a merge-added delegating stub onto the method that carries the body"
  触发面: 只沿 `carrier-stubs.txt` 的行;并且
          "A MinecraftForge or NeoForge mod moves only where its carrier's own patched class has vanilla's
           signature as the body (or, for a name-only selector, only the widened overload) — the row's forge=/neo= column"
```
`SpriteContents.<init>` 这一对**没有进 `carrier-stubs.txt`**(表里没有该行),所以 Sodium(NeoForge 家族)的选择器
没被搬家。修复即:把这一行按表格式补进 `carrier-stubs.txt`(stub = 4 参 `<init>`,delegate = 5 参 `<init>`,
`neo=` 按 NeoForge patched 的事实填),`MixinStubRebind` 就会把两个 `@WrapOperation.method` 从 `<init>` 绑到装 body 的 5 参重载,
`PUTFIELD originalImage` 锚点于是存在,旗标被扫出来,CUTOUT 不再被降到 SOLID。

替代(更窄)做法:像 `FabricSectionCompilerMixinAdapter` 之于 Indigo 的 `SectionCompiler.compile` 那样,
写一条 Sodium 专用适配器,直接把两个 guest mixin 的 `method=["<init>"]` 改成 5 参描述符。
两种都守住同一条:**锚点搬到装 body 的那次调用上,不改 handler 语义。**
