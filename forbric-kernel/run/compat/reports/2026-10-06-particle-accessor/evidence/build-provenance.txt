## Artifact hygiene — why there is a superseded first run

The first assembly of `kernel-fix.jar` (sha256
`b4247eaebe75a2f42f52e19c39f7adf90cfde6639ab7189e847c4a3a193ba24b`) was packed from the same sources, but this
working tree's `build/classes/java/main` and `build/resources/main` had accumulated **pre-existing stale duplicates**
from earlier lanes on this machine:

- 1413 `X N.class` files (e.g. `net/fabricmc/api/ClientModInitializer 2.class`), mostly dated 2026-10-04;
- 7 `X 3.*` resources (`net/forbric/kernel/mixin/carrier-stubs 3.txt`,
  `META-INF/services/org.spongepowered.asm.service 3.IMixinService`, …).

Every sampled `X N.class` is **byte-identical** to its `X.class`, so the duplicates cannot change behaviour (the JVM
resolves a class by its internal name, and both candidates carry the same bytes) — and that first run did read
`run=PASS world=true frames=1 strict=TRUE` with the same marker counts. But the 0.3.5-beta release capture
explicitly verifies "0 duplicate-name classes (' N.class') in the jar", so a jar carrying 1420 of them is not a
valid stand-in for the tip bytes. The debris was deleted, the boot half rebuilt, and the run re-measured against the
clean jar; the clean boot half's entry set is the released one exactly.

Verified before the re-measure: deleting the debris and running `jar` again does **not** regenerate it — the
duplicates were stale deposit, not a live build behaviour.

Both runs are recorded in `evidence/gate-reading.txt` and `evidence/console-markers.txt` (the superseded one with
its sha and reading). The pre-registered criteria were not touched.
